1. Why use Brevo?

A web application often needs to send password resets, account confirmations, invoices, alerts and contact-form acknowledgements. Sending directly from a home connection or small server can be difficult because recipient providers evaluate IP reputation, DNS authentication, bounce behaviour and abuse signals.

Application sending

Your application hands the message to Brevo by SMTP or API, and Brevo performs the internet-facing delivery work.

Delivery feedback

Logs and webhooks can report sent, delivered, deferred, bounced, blocked, opened and clicked events.

Marketing tools

Contacts, lists, segments, campaigns and automations provide a separate newsletter workflow.

Key idea: Brevo can be an outbound delivery service without replacing your normal mailbox or IMAP server.

3. What Brevo is—and what it is not

Brevo can provideIt does not automatically replace
SMTP relay and transactional email APIYour website, application or database
Templates, logs and delivery eventsYour registrar or authoritative DNS provider
Campaigns, contacts and automationsA normal IMAP mailbox for every user
Inbound email parsingYour local archive or groupware platform

A common LocalBox design keeps incoming mailbox service separate and uses Brevo only for outgoing application mail.

4. Transactional email

Transactional email is generated because a user or system event occurred: password resets, verification messages, invoices, receipts, contact acknowledgements and server alerts.

Application event → select template and data → submit by SMTP or API → Brevo queues and delivers → webhook reports result

Templates can accept variables such as customer name, invoice number or verification URL. Transactional messages still require valid authentication, lawful content and responsible bounce handling.

5. SMTP relay

SMTP relay is often the easiest integration because many frameworks already support SMTP. Your application connects to Brevo using encrypted authenticated SMTP credentials, rather than delivering directly to the recipient.

SMTP host: supplied by Brevo
Port and TLS mode: supplied by Brevo
SMTP login: account credential
SMTP key: dedicated sending secret
From address: verified sender
Do not use a normal account password in source code. Use a dedicated SMTP credential and load it from an environment variable or secret store.

6. Email API

The API approach sends a structured HTTPS request. It is useful for templates, attachments, tags, scheduling, personalisation and detailed error handling.

POST /v3/smtp/email
Headers: api-key, Content-Type: application/json

7. Domain authentication

Domain authentication helps recipient systems verify that Brevo is authorised to send using your domain. Brevo provides account-specific DNS values for verification, DKIM and DMARC.

DKIM

Brevo signs the message and recipients verify it with a public DNS key.

DMARC

DMARC publishes policy and reporting and checks alignment with the visible sender.

Sender alignment

The authenticated domain should align with the domain used in the From address.

example.com DNS
├── Brevo verification record
├── DKIM selector record(s)
└── _dmarc.example.com TXT policy

dig example.com TXT
dig selector._domainkey.example.com
dig _dmarc.example.com TXT
Do not copy example values into production. Use the exact values shown in your own Brevo account. In Cloudflare DNS, authentication records are DNS records, not orange-cloud web hostnames.

8. Campaigns, contacts and segments

Campaigns are newsletters, announcements or promotional messages sent to a selected audience. They are different from password resets, invoices and other essential transactional messages.

Contacts → lists / segments → campaign → test → schedule → send → opens / clicks / unsubscribes

Contact data should include

  • Where and when the address was collected
  • What the person consented to receive
  • Attributes used for segmentation
  • Unsubscribe and blocklist status
Good practice: keep marketing and transactional workflows separate because their consent, templates, metrics and blocklist behaviour differ.

9. Automations

Automations run workflows when a trigger occurs, such as a contact joining a list, clicking a link, or reaching a date.

Trigger: contact joins "New Students"
    ↓
Send welcome message
    ↓ wait
Check lesson link
    ├── clicked → send next lesson
    └── not clicked → send reminder

Automations should not silently override consent. Decide which messages are marketing, which are transactional, and how unsubscribes are handled.

10. Webhooks and delivery events

A webhook lets Brevo send an HTTP request to your application when an event occurs, such as delivered, deferred, bounced, blocked, opened, clicked, complaint or unsubscribed.

Brevo event → HTTPS POST /webhooks/brevo → verify → queue or store → return quickly

Store enough to correlate events

  • Local message ID
  • Brevo message ID
  • Recipient and event type
  • Timestamp and bounce reason
Return quickly: validate the request, store or queue it, and respond successfully. Make processing idempotent because retries may occur.

11. Inbound email processing

Brevo can also support inbound email parsing through webhooks. This is useful when an application needs customer replies or support messages as structured data.

Customer email → inbound service → parsed message → webhook → ticket, attachment or workflow

Inbound processing is not the same as giving every user an IMAP mailbox. Decide whether you need automated ingestion, human mailbox access, or both.

13. Basic setup workflow

  1. Create a Brevo account and review current limits.
  2. Add and verify a sender identity or domain.
  3. Publish the account-specific DKIM, verification and DMARC guidance.
  4. Confirm authentication in Brevo.
  5. Create an SMTP key or API key.
  6. Store the credential outside source code.
  7. Send tests to several mailbox providers.
  8. Inspect transactional logs.
  9. Create a webhook endpoint for events you need.
  10. Correlate Brevo message IDs with local records.
  11. Handle bounces and blocked recipients.
  12. Document key rotation and revocation.
BREVO_SMTP_HOST=from-brevo
BREVO_SMTP_PORT=587
BREVO_SMTP_USER=from-brevo
BREVO_SMTP_KEY=secret
BREVO_FROM_EMAIL=noreply@example.com
BREVO_WEBHOOK_SECRET=secret

14. Go SMTP example

A production mailer should read settings from the environment, use the provider's current TLS mode, authenticate with a dedicated key, and return useful errors.

host := os.Getenv("BREVO_SMTP_HOST")
port := os.Getenv("BREVO_SMTP_PORT")
user := os.Getenv("BREVO_SMTP_USER")
key := os.Getenv("BREVO_SMTP_KEY")
from := os.Getenv("BREVO_FROM_EMAIL")

auth := smtp.PlainAuth("", user, key, host)
addr := net.JoinHostPort(host, port)
err := smtp.SendMail(addr, auth, from, []string{to}, []byte(message))
if err != nil {
    return fmt.Errorf("send through Brevo: %w", err)
}
Confirm the current settings: SMTP host, port and TLS behaviour can vary by provider configuration. Do not blindly copy an example into production.

15. Security and secrets

Separate credentials

Use different credentials for development, testing and production where possible.

Restrict access

Only the service that sends mail should read the sending key.

Rotate keys

Document replacement, deployment and revocation of old credentials.

Protect webhooks

Use HTTPS, a secret or signature check, size limits and idempotency.

Never commit keys to Git. If a key appears in source, a screenshot or a public log, revoke it and create a replacement.

16. Deliverability and reputation

Using a relay does not guarantee inbox placement. Recipient systems still evaluate authentication, content, recipient engagement, complaint rates and sending behaviour.

  • Authenticate the domain used by the visible sender.
  • Send to legitimate recipients who expect the message.
  • Remove hard-bouncing and invalid addresses.
  • Use clear sender names and honest subjects.
  • Provide unsubscribe handling for marketing communication.
  • Avoid sudden unexplained volume spikes.
  • Monitor blocked, deferred, complaint and bounce events.

Brevo's current guidance emphasises domain authentication and DMARC alignment. An unrelated authentication domain can still fail alignment checks.

18. When Brevo may be unnecessary

  • The system never sends email outside a private network.
  • Your host already includes a suitable authenticated transactional relay.
  • You operate a well-managed mail system with appropriate reputation.
  • The application sends only a few internal alerts.
  • Another provider is required for compliance, residency or an existing contract.

Choose Brevo when it solves a real delivery, campaign, automation or integration problem.
