Cloudflare Services and Why We Use Them

Learn how Cloudflare can sit between a domain and your servers to provide DNS, HTTPS, reverse proxying, caching, DDoS protection, firewall rules, private tunnels, access control and email routing.

1. Why use Cloudflare?

A domain name does not host a website, secure a server or forward email. It gives people a name to use. Cloudflare provides several services around that name: DNS, reverse proxying, HTTPS at the edge, caching, traffic filtering, tunnels and email routing.

Reach services

Publish names such as www.example.com and point them to the correct destination.

Protect web traffic

When a web record is proxied, visitors connect to Cloudflare first, where requests can be filtered, cached and forwarded.

Reach local servers

Cloudflare Tunnel lets a server make an outbound connection without exposing inbound ports for supported applications.

Key idea: Cloudflare is a platform of separate services. You can use DNS alone or combine it with proxying, Tunnel, Access, Workers and email routing.

These roles can be split across different providers. A domain can be registered in one place, use Cloudflare nameservers and point to a LocalBox server elsewhere.

4. Authoritative DNS

When Cloudflare is authoritative, your registrar delegates the domain to Cloudflare nameservers. Cloudflare then answers public queries for the zone.

DNSSEC

DNSSEC adds signatures that allow resolvers to validate DNS answers. During a nameserver migration, handle the old registrar DS record and the new provider's DNSSEC details carefully.

Migration warning: stale DNSSEC delegation can make a correctly configured domain appear unreachable.

5. The orange-cloud proxy

Cloudflare records can be proxied or DNS only.

Proxied

Visitors connect to Cloudflare first. Cloudflare can apply HTTPS, caching, DDoS protection and WAF rules before forwarding requests to the origin.

DNS only

DNS returns the origin target directly. Cloudflare provides the DNS answer but does not sit in the traffic path.

Public HTTP and HTTPS records are common proxy candidates. Mail hostnames, MX targets, verification records and unsupported protocols should usually remain DNS only.

Email warning: do not orange-cloud an ordinary SMTP or IMAP hostname.

6. HTTPS and certificates

Cloudflare can present an edge certificate to visitors, but the connection from Cloudflare to the origin should also be secured.

Visitor to edge

Cloudflare presents the public certificate for the hostname.

Edge to origin

Use strict TLS validation with a valid origin certificate.

Redirects

Keep HTTPS redirects consistent to avoid loops.

curl -I https://example.com
openssl s_client -connect example.com:443 -servername example.com

Cloudflare can simplify certificate management at the edge, but it does not remove the need to secure and maintain the origin.

7. CDN and caching

A content delivery network stores suitable static content closer to visitors, reducing repeated work and bandwidth on a small origin such as a Raspberry Pi.

Good cache candidates

Images, stylesheets, scripts, public downloads and versioned assets.

Usually dynamic

Dashboards, personalised pages, shopping baskets and private API responses.

Risk

Do not cache private or personalised responses where another user could receive them.

8. DDoS, WAF and firewall rules

When traffic is proxied, Cloudflare can filter attacks before they reach the origin. The WAF and custom rules can inspect web requests and apply allow, block, challenge or log actions.

ControlPurpose
DDoS protectionMitigate large volumes of malicious traffic.
WAFDetect common web exploit patterns.
Custom rulesApply conditions to paths, countries, identities or request properties.
Rate limitingReduce repeated abuse of login and API endpoints.

If the origin IP remains public, attackers may bypass Cloudflare. Restrict origin access to Cloudflare traffic or use Tunnel for applications that should not have an exposed web listener.

9. Cloudflare Tunnel

Cloudflare Tunnel runs cloudflared on a server and creates an outbound connection to Cloudflare. Requests for a chosen hostname can then be carried through the tunnel to a local service.

Visitor → Cloudflare edge → encrypted tunnel → cloudflared → localhost:8080
  • No router port forwarding for the published application.
  • No requirement for a public IPv4 address.
  • The origin can remain behind NAT or a restrictive firewall.
  • Cloudflare security services can sit in front of the application.
Protocol scope: Tunnel is excellent for supported web and private-network use cases; it does not automatically proxy every arbitrary internet protocol.

10. Cloudflare Access and Zero Trust

Access can require a user or device to authenticate before Cloudflare forwards a request to a protected application. This is useful for internal dashboards, staging sites, administrative tools and private documentation.

User requests admin.example.com
Cloudflare Access checks policy
Approved identity signs in
Cloudflare forwards to the application

Keep access policies narrow. Grant the correct people access to the correct application rather than treating everyone inside one organisation as fully trusted.

11. Email Routing and mail DNS

Email Routing can accept incoming mail for a domain address and forward it to a verified destination or an email-handling Worker.

Useful for

Addresses such as info@example.com when you do not need to operate a full mailbox server.

Not the same as

A complete IMAP mailbox, outbound SMTP service or self-hosted mail server.

MX, SPF, DKIM and DMARC records must match the service actually handling mail. Web records can be proxied, but ordinary mail hostnames should usually remain DNS only.

12. Workers and automation

Workers run code at Cloudflare's edge. They can redirect URLs, modify headers, implement lightweight APIs, process routed email or check an identity token before forwarding a request.

  • Redirect old URLs.
  • Add security headers.
  • Build a small JSON API.
  • Process incoming Email Routing messages.
  • Connect an edge request to another service.
Architecture rule: use Workers for edge logic and keep origin responsibilities, logs and failure handling clear.

14. When Cloudflare is not needed

  • The service is completely local and never needs internet access.
  • A private Tailscale or Headscale mesh already provides all required access.
  • The hosting platform already handles DNS, CDN and certificates adequately.
  • You deliberately want clients to connect directly to the origin.
  • The protocol is not supported by the Cloudflare product you intend to use.

Use Cloudflare when it solves a real routing, security, availability or management problem.

15. Basic setup workflow

  1. Add the domain to Cloudflare.
  2. Review imported DNS records carefully.
  3. Handle old DNSSEC delegation before changing nameservers.
  4. Change the registrar nameservers to Cloudflare's assigned nameservers.
  5. Test A, AAAA, CNAME, MX and TXT records.
  6. Choose which web records should be proxied.
  7. Configure strict HTTPS to the origin.
  8. Enable DNSSEC again after migration is stable.
  9. Add cache, WAF, Tunnel or Access only where needed.
  10. Record the final design and keep a rollback plan.

dig example.com A
dig example.com MX

17. Suggested exercises

  1. Draw the difference between a registrar, DNS provider and web host.
  2. Create one proxied web record and one DNS-only mail record.
  3. Use dig to inspect A, MX and TXT answers.
  4. Design a Tunnel route from app.example.com to a local port.
  5. Write an Access policy for an administrator and a student.
  6. Explain why MX and SPF records cannot simply be copied from another domain.
  7. Identify which website assets are safe to cache.
  8. Compare Cloudflare Tunnel with Headscale/Tailscale for administration.
